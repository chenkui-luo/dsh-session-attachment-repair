## 目录布局

`<DSH_HOME>` 默认为用户主目录下的 `.dsh`，可用环境变量 `DSH_HOME` 覆盖。

```text
<DSH_HOME>/
  sessions/<工作区目录名>/<会话 id>/session.v3.jsonl.zstd   # 追加式会话日志
  attachments/v1/
    objects/<前两位>/<sha256>        # 图片对象（内容寻址）
    file-objects/<前两位>/<sha256>   # 文件附件对象
    files/<前两位>/<sha256>/<文件名>  # 文件附件的可读副本
    request-images/                  # 派生请求图，可清空后重建
  storages/
    workspace.json                   # 工作区与会话登记
    session_projcache/sessions/*.json # 投影缓存（含 contextPressure 等）
```

## 会话日志格式

- 整个文件是**多个 zstd 帧首尾相接**，每帧解压后是若干整行 JSON。一次追加可能产生新的一帧。
- 逐帧解码要自己走帧头：zlib 的一次性 zstd 解码只返回第一帧的内容，直接把整份文件丢进去会得到"只有几行"的假象。
- 行内容不可压缩理解：第一行是会话头（`type: session`、`version`、`id`、`cwd`、可选的 `isSeeded`/`inheritedEventCount`），其余是按 `seq` 递增的事件。
- 修复时保持帧边界、保持每帧内行序，只替换需要改的行。

## 附件引用与校验

消息内容块有两种附件形态：

```json
{ "type": "image", "attachment": { "attachmentId": "sha256:<64 hex>", "name": "shot.png", "bytes": 111608, "width": 1440, "height": 5600 } }
{ "type": "file",  "attachment": { "attachmentId": "sha256:<64 hex>", "name": "要求.md", "bytes": 860 } }
```

- `attachmentId` 里的 64 位十六进制就是对象文件名，按前两位分目录。
- 图片查 `objects/`；文件附件查 `file-objects/`（或 `files/` 下的同名目录）。任一处存在即可用。
- 读取时会校验 sha256、字节数、宽高；把原图拷回去对不上，会报"元数据不匹配"，不是本流程能修的情况。

## 错误文案对照

| 文案 | 所在层 | 说明 |
| --- | --- | --- |
| `... API request to <基址> failed` | 适配器请求阶段 | 连不上、TLS 失败、被拒；属于网络或代理问题 |
| `... API stream from <基址> failed` | 适配器兜底包装 | 请求准备或流中途抛出非归类异常；**真实原因常被吞掉** |
| `Attachment object is missing.` | 附件读取层 | 会话引用的图片对象不存在，命中本流程 |
| `File attachment object is missing.` | 附件读取层 | 文件附件对象不存在，命中本流程 |
| `stream idle timeout after <n>ms` | 空闲看门狗 | 长时间没有数据，不是附件问题 |
| `HTTP 401/403/429`、`HTTP 5xx` | 服务端响应 | 鉴权、限流、服务端故障 |

判断要点：兜底文案本身不能当结论；换一条模型通道（走另一个适配器）复现，往往能拿到未经包装的真实异常；也可以直接读会话日志里失败那一轮的 `assistant/attempt` / `turn/end` 记录，看是否有 `cause`。

## 为什么必须重启

宿主服务端会把已打开的会话整份留在内存里（含事件与投影）。所以：

- 只改磁盘文件，内存里的会话仍是旧的，下一次发消息照样失败；
- 服务端下次追加事件时会写回这份文件，看起来"改动被吃掉了"；
- 判断改动是否生效，可以看投影缓存里的上下文体量有没有按替换量下降；没降说明读的还是旧状态。

结论：写完必须让用户完全重启服务端，再复验。重启前不要宣称已修好。

## 为什么原图补不回来

附件库是内容寻址存储，读取时同时校验：sha256 与文件名一致、字节数一致、宽高一致，且保存的是规范化之后的图片（未必是原始截图）。因此从项目目录里找回原图再拷进去，哈希和尺寸都对不上，会被判定为损坏。能做的只是把引用替换成占位，让会话可以继续。

## 常见误判

- **以为是网络**：同一时刻别的会话能正常出字，就说明网络与凭据是通的。
- **以为是上下文太长**：上下文体量接近的另一个会话能正常发消息，就不是长度问题。
- **以为修好了**：没有重启就复验，得到的是假阴性；重启后仍失败，说明还有第二个原因。
- **以为占位会丢内容**：被替换的只有已经无法发送的附件引用，正文、工具结果和文件附件（对象仍在时）都不动。
